# 阶段: 闭环报告（Step 4）

⚠️ 前置硬约束：Step 3 收尾问题获用户确认后才开始。未确认就开始 = 违规。

## 流程（两段式）

```
1. 草案 + 后模拟走查（连续完成，中间不停）
   → 按"草案模板"输出（对话展示，不写文件；发前先过审查门禁）
   → 立刻跑后模拟走查，走不通就修，修完再走
   → 草案 + 走查结果 + 修复记录 + 需用户决策项 一起呈现
   → ⚠️ 停下问用户: "方案和后模拟走查结果 OK 吗？确认后我写 CLOSURE.md。"

2. 用户确认后，写 CLOSURE.md 落盘（完整闭环报告 = 草案 + 后模拟结果）
```

## 草案模板（对话展示，不写文件）

⚠️ **发草案前先过审查**：Read `references/05-checklists.md`，按"系统在乎什么"挑相关组逐条追问 + 过交付门禁，**无 CRITICAL 项才发草案**；命中 CRITICAL 先修方案再发。
- **断言可测**：方案里每个断言锚到可测标准了吗？"体验好/性能佳/易维护"这类形容词断言，能说出怎么测、阈值多少吗？不可测的断言 = 未定的验收标准 → 标「需用户决策」，不许带进 CLOSURE.md。

```markdown
# 闭环报告（草案）: <项目名>

## 1. 项目骨架
- 目录结构（精确到文件）
- 技术栈 + 版本号
- 初始化命令（复制粘贴就跑）

## 2. 复用施工单
| 模块 | 来源(repo@file) | 解决什么问题 | 需求真有这问题? | 复用方式 | 裁剪/改动 | 理由 |
|------|-----------------|-------------|----------------|---------|-----------|------|
| <模块A> | repoX@src/auth/login.ts | 登录认证 | 是 | 直接复制 | 去掉 OAuth，只留邮箱 | 需求只需邮箱登录 |

## 3. 实施路线图
### Phase 1: <名称>（依赖: 无）
- [ ] 步骤 1 — 做什么、参考什么
- [ ] 步骤 2
- 验证: <怎么算做完>

## 4. 自研施工单
| 模块 | 为什么没得复用 | 实现思路 | 参考 |
|------|--------------|---------|------|

## 5. 扩展点与关键决策（从 Step 2 设计草案搬入，施工时照此预留）
| 位置（schema/对外契约/核心抽象/安全边界） | 预留扩展位 | 为什么贵且大概率要变 | ADR |
|------|------|------|------|
| 订单表 | version 字段 | 数据回填迁移成本高，未来加乐观锁/幂等 | ADR-2 |

无扩展点的项目明写「本项目无扩展点」，不留空也不删节。
```

## 后模拟（闭环自检）

> **后模拟 = 模拟执行这个计划，走一遍看能不能通。不通就修，修完再走，直到通为止。核心目标是验证整个流程可执行，不是逐项打勾。**

### 走查时参考以下材料（非强制，辅助发现漏洞）

| 参考材料 | 来源 | 怎么用 |
|---------|------|--------|
| 前模拟遗漏清单 | Step 3 | 每项遗漏在路线图里被覆盖了吗？没覆盖的补上 |
| 可行性裁决 | Step 3 | proceed 的前提条件满足了吗？改/转向的调整落实了吗？ |
| 复用候选 | Step 3 researcher | 计划里引用的复用来源，实际能拿到吗？裁剪清单落实了吗？ |
| phase0 anti_goal | Step 1 | 方案有没有悄悄纳入明确不做的功能？ |

### 走查方式
挑 1-2 个核心用户场景，按路线图 Phase 顺序逐步走查。每一步：
1. 这一步需要的输入（数据/模块/配置）在前面的步骤里产出了吗？
2. 参考上表扫一眼，有致命漏洞吗？

走查完**抽查 2 条 repo@file:line 来源标注**：文件真的存在、内容真的支撑该声明？抽查不过的候选降级为「LLM 推测」或重读代码再定，别带进 CLOSURE.md。

### 走不通时的处理

| 情况 | 判断标准 | 处理方式 |
|------|---------|---------|
| 简单 | 缺配置、漏步骤、少依赖声明 | **LLM 直接补**，记录修复 |
| 中等 | 需要找方案但方向明确（如"缺一个限流中间件"） | **拉 researcher 流程**，搜 GitHub 找现成方案，补上后继续走 |
| 复杂 | 动架构、动范围、多模块冲突、推翻前一步决策 | **停下来问用户**，说明断点和选项 |

### 输出

```markdown
### 场景走查: <场景名>
| 步骤 | Phase | 能通？ | 问题 | 处理 |
|------|-------|--------|------|------|
| 用户注册 | Phase 1 | ✅ | — | — |
| 下单支付 | Phase 2 | ❌ | 支付回调没处理 | 中等 → 搜 repoX@src/payment/webhook.ts，补进 Phase 2 |

### 修复记录
| # | 原问题 | 修复 | 来源 |
|---|--------|------|------|
| 1 | 支付回调缺失 | 复用 repoX webhook 模块 | repoX@src/payment/webhook.ts |

### 需用户决策
- <断点描述> — 选项 A / 选项 B
```

### 退出条件
- 核心场景全部走通，或
- 剩余问题全是「需用户决策」级别
- 达到任一条件 → 把草案 + 走查结果一起呈现，⚠️ **问用户确认后才写文件**：

> **"方案和后模拟走查结果 OK 吗？确认后我写 CLOSURE.md。"**

## 写文件

用户确认后，将完整闭环报告（草案 + 后模拟结果）写入 `CLOSURE.md`。

每个模块必须标 **复用 / 改造 / 自研**，复用/改造必须标注来源 repo + 文件路径，且注明裁剪掉的部分。

## 经验回流（CLOSURE.md 落盘后执行，不做不算闭环）

> **强制一问**："这次设计踩了/避了什么值得记的坑？"——含修正过的误判、用户关键裁决、复用裁剪教训。没有值得记的就明说「本次无可回流经验」，不硬凑。

回流前先 Read 对应领域 experience 文件（架构→`experience/arch.md` / 智能体→`experience/agent.md` / 通用→`experience/general.md`），对照已有条目**三选一**：

1. **实质新坑**——「坑→后果→对策」三元组无实质相同条目 → 按 U 编号递增新增
2. **老坑新证据**——同一坑，但带来新来源/新后果/新对策细节 → 并入原条目，追加来源标注
3. **重复** → 什么都不写

⚠️ 判重复看三元组实质，不看标题像不像。新条目遵循各文件头部格式约定：`- **U<编号> <标题>**（[来源]）：坑 → 后果 → 对策。`
