**共享踩坑库**：researcher 已 Read 过 `references/04-pitfalls.md`（见 researcher.md 硬约束 3），直接复用上下文里的结论，**不重复 Read**（仅上下文缺失时才补读：架构 #01-23；含智能体另加 #A01-A42）。踩坑库列过的问题优先核对设计有没有覆盖。

**硬约束**：每条声明必须引用 GitHub 代码(repo@文件:行号) 或 标注「LLM 推测」。**搜索角度分工** — researcher 搜「同类项目可复用实现」；前模拟搜「这类项目的坑/教训/issue」，角度不同不重复。researcher 已列过的 repo 直接引用不重搜。**不重复扫描** — Step 2.4 韧性设计已逐项核对过的超时/重试/熔断/降级/资源上限/慢依赖，前模拟不重复扫，直接引用其结论；前模拟只扫独有的：运营需求/合规/用户体验/监控/范围越界/想当然假设/同类坑。

## 四类遗漏扫描

### 1. 用户没提但可能需要的
- 边缘场景：并发/失败/超时/重试/断网
- 运营需求：对账/报表/告警/客服/工单
- 合规要求：隐私/审计/数据保留
- 用户体验：错误提示/引导/空状态/异常恢复
- 监控可观测：日志/指标/链路追踪/健康检查
- 范围越界：对照 phase0 `anti_goal`，方案是否悄悄纳入了明确不做的功能

### 2. 用户可能想当然的假设
- 规模假设：峰值多少？活动期 10x？秒杀场景？
- 平台假设：多端数据同步？登录态打通？
- 业务假设：支付→退款？对账？争议？部分退款？
- 集成假设：第三方挂了怎么办？超时？降级？
- 数据假设：读多写少？冷热数据？

### 3. 同类项目踩坑检索（经验 + GitHub）
先凭 LLM 经验列这类项目常见坑（例: 点餐=库存并发/支付回调/商家权限/跑单纠纷），再 GitHub 搜索验证补充（推荐 `search_github`，兜底 gh/curl，角度: 坑/教训/issue）：
- 同类项目踩过的坑
- 同类系统常见错误
- 跨界借鉴：类似问题在其他领域怎么解决

### 4. 完整性穷举（Steelman + Actor + Premortem）
- **Steelman 列全**：列出所有子系统/角色/核心实体，别只从主用户视角出发（例: 点餐小程序不能只有顾客端，还要商家后台、平台管理端）。Step 2 结构设计已列出的子系统/角色直接引用，不重穷举；本类只补漏
- **Actor 穷举**：至少覆盖终端用户/业务方/管理方三类，列举不出新角色即止。每个角色答 4 问——要哪些功能页面？需要哪些数据表？数据和其他角色共用还是隔离？有什么权限/审计要求？
- **Premortem 失败倒推**：假设上线 3 个月后失败（弃用/流失/被投诉），倒推失败原因链，反向查遗漏

发现**整个子系统/角色缺失**（如漏了商家后台）不是普通遗漏——在遗漏清单「类别」列标「设计级」，Step 3 整合时单独列出，由用户决定回 Step 2 补设计还是按普通遗漏进路线图。

四类扫描的发现统一并入下面的遗漏清单，同一遗漏只记一次；「影响实际交付」的遗漏必须有施工动作，次要遗漏也写一句方案方向，实在给不出标「已知风险」。
