# Design Lab

单命令走完「需求 → 设计 → 复用 → 验证 → 闭环」，固定停 4 个决策点（Step 1 澄清最多两轮）。

**三合一融合模型**：以 deep-analysis 的调研闭环为主干，把 arch-designer 的知识注入「复用评估」环节（判断能复用/怎么复用/砍哪些），agent-designer 知识按需条件加载（无智能体不触发）。

## 触发判断

复杂需求才执行，满足任一即复杂：
- 多模块 / 需要架构决策
- 涉及外部集成（支付/登录/第三方 API）
- 涉及智能体（agent/AI 助手/工具调用/多智能体/RAG）
- 需要调研竞品 / 复用候选 / 技术选型
- 存在规模/并发/安全风险
- 用户说"做个 XX 系统/平台"，范围模糊

**简单需求不执行**，直接给 1 句方案。

## 流程总览

```
/design-lab <需求>
  ├─ Step 1  需求澄清 + 路径选择（phase0 格子驱动，≤2 轮 × 每轮 ≤3 问）── 用户答 ①
  ├─ Step 2  领域设计(先设计后找码) ★产出「我们的问题清单」── 用户确认 ②
  │          ├─ Read flows/arch-flow.md 默认加载 (仅极小项目跳过): 估算/选型/结构/扩展点/韧性
  │          └─ 含智能体    → 追加 Read flows/agent-flow.md (BDD/模式/结构/护栏测试)
  ├─ Step 3  researcher → 前模拟 → 整合 连续执行（中间不停）
  │          ├─ researcher: GitHub 找复用 + 问题拟合四问 + 裁剪清单
  │          ├─ 前模拟: 遗漏扫描 + 完整性穷举(Actor 穷举/Premortem)
  │          └─ 整合: 复用Top3 + 遗漏Top5 + 裁决 ── 用户确认 ③
  └─ Step 4  草案→后模拟→一起呈现──用户确认 ④──→ 写 CLOSURE.md → 经验回流（对比去重）
        ⤴ 任意时刻冒出新需求 → 暂停，按硬规则 6 处理
```

## Step 1: 需求澄清 + 路径选择

⚠️ **提问以 phase0 能否写全为准，不数问题个数**（得到回答前不调研、不写方案）：

- **格子驱动**：phase0 五格（requirement / platform / scale / existing_code / anti_goal）+ 一项判断（是否含智能体，决定 Step 2 加载哪个 flow）。哪个格子填不上就问哪个；格子全满 → 一问不发，直接锁定 phase0 进 Step 2
- **每问必落到具体格子**：别问"还有什么要补充的"这类无锚点的开放大问题
- **硬刹车**：单轮最多 3 问。问满仍有大缺口 → 停止追问，告知用户"信息缺口太大，建议先给一份粗需求文档再启动"，比连环拷问诚实
- **第二轮补漏式**：用户答完暴露新缺口 → 可追问一轮（仍 ≤3 问），只问新缺口，已答的不再碰；最多两轮，两轮后仍缺的格子标「已知风险」带进 Step 2

澄清完问路径：

> **"直接给方案，还是先调研再给？"**

- 选「直接给」→ 跳过调研/复用，凭经验直接给方案（标「LLM 推测」），仍用已锁定的 phase0
- 选「查询」→ 走完整流程

锁定范围产出 `phase0`（JSON 见 `stages/simulator.md`）。

## Step 2: 领域设计（先设计，后找码）

按需求类型加载对应流程，**先设计出问题清单，再带着问题去找码**（问题拟合才有依据）：

- **架构/系统类** → **Read `flows/arch-flow.md`**（默认加载，仅极小项目跳过——单模块/无持久化/无外部调用/无并发，四条全满足才算）：场景与信封估算 → 模式选型 → 结构设计（含扩展点预留）→ 韧性设计
- **含智能体** → 追加 **Read `flows/agent-flow.md`**：BDD 场景 → 模式选型 → 结构设计 → 护栏与测试规划

★ **核心产出：「我们的问题清单」**——本系统/智能体碰了哪些容易出事的问题，每条对应 `references/03-problem-solution-map.md` 的哪条问题。**Step 3 researcher 拿这份清单做问题拟合**。

⚠️ **强制收尾（必须问，答完才进 Step 3）**：

> **"设计草案 + 问题清单 OK 吗？确认后我才进 Step 3 找复用。"**

## Step 3: 调研 + 前模拟 + 整合（连续执行，中间不停）

基于 phase0 + Step 2 设计产物，主 Agent 顺序执行三个阶段（不 spawn 子代理，产物留在对话内传递）：

1. **researcher** — **Read `stages/researcher.md`**。带问题清单 GitHub 找具体复用，每个候选过**问题拟合四问**（它解决什么问题 / 我们需求里真有吗 / 解法对症吗 / 怎么复用）+ **裁剪清单**（保留/砍掉/改掉）。
2. **前模拟** — **Read `stages/simulator.md`**。扫四类遗漏（没提但需要的 / 想当然假设 / 同类踩坑 / 完整性穷举），每条配施工动作。
3. **整合** — 直接输出：

```
## 可行性整合

### 复用候选 Top 3（含裁剪）
| repo | 解决什么问题 | 需求真有这问题? | 复用方式 | 裁剪掉哪些 |
|------|-------------|----------------|---------|-----------|

### 遗漏 Top 5（从前模拟）
| 遗漏 | 严重度 | 施工动作 | 来源 |
|------|--------|---------|------|

### 设计级遗漏（如有）
> 整个子系统/角色缺失（前模拟「设计级」条目）→ 回 Step 2 补设计，还是按普通遗漏进路线图？请用户在此裁决。

### 裁决
proceed / 改 / 转向 / kill
理由: <一句话>
```

⚠️ **Step 3 强制收尾问题（必须问，答完才进 Step 4）**：

> **"方向对吗？可行性 OK 吗？有要调整的吗？确认后我出闭环报告。"**

## Step 4: 闭环报告（草案 + 后模拟 → 确认 → 落盘）

⚠️ **前置硬约束：Step 3 收尾问题获用户明确确认之后才开始 Step 4**。未确认就开始 = 违规。

**Read `stages/closure.md`** 执行：草案（先过审查门禁）→ 立刻跑后模拟走查 → 草案 + 走查结果一起呈现 → 一次确认 → 写 CLOSURE.md。

⚠️ **Step 4 强制收尾**——草案和后模拟走查结果一起呈现后必须问：

> **"方案和后模拟走查结果 OK 吗？确认后我写 CLOSURE.md。"**

## 硬规则

1. **复杂需求才触发** — 简单需求直接忽略
2. **复用优先** — 选「查询」时先搜 GitHub，有现成直接引用，不从零想方案；选「直接给」时不搜索，凭经验直接给（标「LLM 推测」）
3. ★**每条问题/遗漏必须配解决方案** — 复用候选过「问题拟合四问」+ 出裁剪清单；**前模拟扫出的遗漏，无复用的写自研思路，实在给不出标「已知风险」**，不能只列不留
4. ★**arch-flow 默认必加载**（仅极小项目跳过，判定标准见 Step 2）；**无智能体的需求不加载 agent 知识**（不触发 agent-flow，避免无关内容）
5. **每条声明标注来源** — GitHub 代码(repo@文件:行号) 或 「LLM 推测」
6. **需求变更即停** — 任意时刻冒出新需求（流程中/闭环报告后）：暂停 → 记录 → 评估影响 → 回退对应 Step（动范围→Step1、动设计→Step2、仅追加→闭环报告需求池）→ 用户确认后继续。绝不默默按旧需求做到底
7. **问完必停** — 每次向用户提问（澄清+路径/Step 2 设计/Step 3 整合/Step 4 闭环）后必须停下等待回答，得到答复前绝不推进下一步。后模拟走查结果必须先确认，确认后才写 CLOSURE.md
