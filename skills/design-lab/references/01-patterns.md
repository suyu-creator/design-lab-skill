# 01 · 架构模式库

> 按"遇到的问题"对症选型。口诀：**能不用就先别用 → 对症下药 → 付得起代价才上**。
> 每个模式讲四件事：①解决什么问题 ②长什么样 ③代价 ④什么时候别用——**看不到代价，就等于没学会这个模式**。
> 来源：awesome-architecture《04-十大核心架构模式》提炼 + 架构最佳实践。

## 选型决策口诀

```
Step 0：能不用模式就先别用 —— 最简单的分层单体能不能解决？能 → 就这样
   ↓ 解决不了，才往下问
问 1：我遇到的到底是什么问题？对症，别对时髦（看下表）
问 2：这个模式的代价我现在付得起、也愿意付吗？付不起 → 先别上，记一笔以后可能要
```

## 一、基础与默认

### 1. 分层架构 Layered
- **解决**：把系统按关注点横向切层（表现/业务/数据），每层只跟相邻层打交道——别把所有东西搅成一锅粥。
- **结构**：表现层 → 业务层 → 数据访问层 → 数据库，每层只调用下一层，不越级不反向。
- **代价**：穿透成本（简单查询也要穿层写样板代码）；层间贫血传递对象。
- **别用**：几乎永远适用，问题不在用不用而在**别教条**——别为了纯粹禁止合理的跨层优化；分层是代码组织方式，不代表每层要独立部署。

### 2. 单体 / 模块化单体 Monolith —— 被严重低估的正确起点
- **解决**：整个应用作为一个可部署单元交付，模块间函数调用而非网络调用——最低的协作和运维成本先把东西做出来。
- **关键**：单体内部**完全可以、也应该分模块**（模块化单体）。模块化单体 ≠ 一团乱麻。
- **代价**：改一行整体重新发布；无法单模块扩容；一个模块崩溃可能拖垮整个进程；边界不清会退化成大泥球。
- **别用**：当组织和规模**真的**到扛不住的程度（见微服务三个前提）。**给新人的硬建议：默认从模块化单体开始，等你真的痛在明确的某处了，再针对那一处拆。先拆了再说几乎总是错的。**

### 3. 微服务 Microservices —— 被严重滥用的成熟期解药
- **解决**：把大应用拆成多个可独立开发/部署/扩容的小服务，各自拥有自己的数据。**它首先解决的是人的扩展性（组织），其次才是机器的扩展性。**
- **结构**：API 网关统一入口 + 多个服务（各带独立 DB），服务间靠网络调用通信。
- **代价**：函数调用→网络调用引入一整座分布式复杂度大山（超时/重试/幂等/跨服务事务/运维爆炸/本地调试难）。
- **别用**——三个前提最好同时满足：
  ```
  前提一：组织规模够大（多团队互相阻塞、共享代码库成瓶颈）
  前提二：有明确的独立部署需求（独立发布节奏/扩容/可用性）
  前提三：已有承接复杂度的平台能力（监控/追踪/CI-CD/编排就位）
  ```
  > 滥用典型画面：五人团队做月活几千的产品，拆十几个微服务，每天耗在服务间为什么调不通上。**微服务常常用来解决你还没遇到的问题，代价是制造一堆你本来不会有的问题。**

## 二、解耦与异步

### 4. 事件驱动 Event-Driven
- **解决**：组件间通过"发生了什么事"协作，而不是"你去帮我做什么"命令——下单成功后要扇出短信/积分/物流/报表，发布者不关心谁在听。
- **结构**：发布者 → 事件总线/消息中间件 → 各订阅者各自响应、互不知情。
- **代价**：整体流程看不见（排查像破案）；事件可能重复/乱序/丢失；最终一致带来短暂不一致。
- **别用**：流程简单、调用关系清晰时硬上 = 把直路绕成迷宫；需要立刻拿到结果的同步场景（按钮点了要马上知道成败）。

### 5. 消息队列 / 异步处理
- **解决**：生产者和消费者之间放缓冲水池，解决三件事：**削峰填谷**（洪峰先进队列后端慢慢消化）、**异步解耦**（耗时活别让用户干等）、**可靠投递**（消费者挂了任务还在）。
- **直觉**：同步像打电话（得等对方接完），异步像发短信（发完就干别的）。
- **代价**：新增必须维护监控的关键基础设施；处理变异步用户拿不到即时结果；**消费逻辑必须幂等**（消息可能被消费两次）；队列堆积本身是新监控对象。
- **别用**：需要同步即时返回的链路别硬塞队列；任务量小、无峰值压力时加队列徒增运维负担。

### 6. 发布-订阅 Pub/Sub
- **解决**：一件事要通知很多方、且通知方不想知道有哪些接收方——一条消息被**所有**订阅者各收一份（广播）。
- **关键区别**：队列 = 一条消息只被一个消费者处理（分活儿）；Pub/Sub = 人人有份（广播）。
- **代价**：全局流程难追踪；订阅者多了扇出成本上升；可靠性语义（至少一次/至多一次）要想清楚。
- **别用**：点对点一对一明确调用杀鸡用牛刀；强一致要立即确认的交互不适合广播式异步。

## 三、读写与前端

### 7. CQRS 读写模型分离
- **解决**：写和读诉求根本不一样（写要严谨强一致，读要快可聚合），硬用同一模型两头不讨好——读远多于写（一次修改千万次浏览）时。
- **结构**：写模型（规则严谨/强一致）→ 数据同步/事件 → 读模型（反范式/可缓存，可多个）。
- **代价**：复杂度翻倍（两套模型 + 可靠同步通道）；读写间通常异步最终一致，产品和用户要接受。
- **别用**：**绝大多数系统不需要 CQRS。** 读写压力差不多、数据量没大到需分开优化时上它 = 自找麻烦。它是读写严重不对称、常规手段压榨干净后的重武器，不是默认选项。

### 8. 客户端-服务端 / BFF
- **解决**：为每种前端（Web/iOS/Android/手表）单独做一个贴身后端，裁剪/聚合后端零散数据成该端最顺手的形状。
- **结构**：各端 → 各端 BFF → 后端核心服务/微服务（核心逻辑只写一份）。
- **代价**：多一层要开发和维护的中间人；团队不大时多个 BFF 间易重复代码；BFF 本身可能膨胀成新小单体。
- **别用**：只有一种前端、或各端诉求高度一致时加 BFF 纯属多此一举。

## 四、加工与扩展

### 9. 管道-过滤器 Pipeline
- **解决**：把处理任务拆成一串首尾相接的处理步骤（过滤器），前一站输出是后一站输入——数据像流水线一站站加工。
- **结构**：校验 → 清洗 → 转换 → 压缩 → 入库，每站只干一件小事、不知上下游，可独立替换/测试/扩容。
- **代价**：整条管线吞吐受最慢一站拖累（木桶效应）；一站失败要想清整条链路怎么回滚/重试；站间传递有序列化开销。
- **别用**：逻辑不是线性流水形态时硬套会很别扭；步骤高度耦合、需频繁互相回头看的场景不适合。

### 10. 微内核 / 插件化 Microkernel
- **解决**：核心稳定、外围多变——稳定最小内核 + 可插拔插件，第三方/用户能在不动核心代码前提下扩展。
- **结构**：稳定内核（基础能力 + 插件契约）← 各插件（多变、可热插拔、可沙箱）。
- **代价**：插件契约一旦定下来很难改（改了所有插件跟着动）；一个烂插件可能拖垮内核（需隔离/沙箱）；内核要预留扩展点，设计难度高。
- **别用**：功能稳定、没有让外人扩展需求的系统搞插件化 = 过度设计。

## 心法（三条）

1. **从简单开始，被痛驱动地演进。** 不要预支未来的复杂度。问题真出现、且痛在明确的某处，再引入对应模式。
2. **模式可以组合。** 真实系统几乎都是分层单体打底，局部用上事件驱动、异步、缓存。不是单选题。
3. **永远能说出代价。** 引入任何模式，若说不清它换走了我的什么（简单性/一致性/可观测性），大概率在跟风。
