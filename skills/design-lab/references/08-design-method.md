# 08 · 架构设计方法（八步 / 信封估算 / ADR / 演进 / 经验库）

> 从 0 设计一个系统的完整方法论。来源：awesome-architecture《07-从0到1设计一个系统》《08-架构决策记录与演进》。

## 一、八步设计流程（从 0 设计一个系统）

```
Step 1 澄清需求        做什么 / 用户 / 规模 / 约束 / 质量属性
   ↓
Step 2 信封估算        流量 / 存储 / 带宽量级（见下节），先算清楚再动手
   ↓
Step 3 定义用例与 API   主流程 + 异常 + 边界的 Given-When-Then；接口长什么样
   ↓
Step 4 数据模型         事实源在哪 / 有哪些实体 / 关系怎么建模 / 哪些要最终一致
   ↓
Step 5 画 Context/Container 图   用 C4：系统边界 → 容器（服务/DB/队列）→ 数据流
   ↓
Step 6 深挖灵魂组件     最核心/最容易出事的组件单独展开（如支付状态机、Feed 扇出）
   ↓
Step 7 找瓶颈          哪里会先崩：热 key / 单点 / 慢路径 / 容量上限
   ↓
Step 8 回顾取舍         每个选型说清代价（换走了什么）；写 ADR 记录
```

**三个心法贯穿全程**：① 先问为什么再看怎么做（每个选择背后都是约束或取舍）；② 没有最好的架构只有最合适的（规模/团队/成本/合规决定一切）；③ 架构会长大（别拿成熟期套 MVP）。

## 二、信封估算（Back-of-Envelope）

不追求精确，只要量级正确。三步：

1. **算请求量**：日活 × 每用户每日请求数 ÷ 86400 ≈ QPS；峰值 = 均值 × 系数（如 5-10x）
2. **算数据量**：每秒写入量 × 保留时长 × 单条大小 ≈ 总存储；留 3-5 倍增长余量
3. **对号入座**：QPS 千级=单机够；万级=要缓存+读写分离；十万级=要分片/分布式；先算清楚，别拍脑袋上分布式

**示例（短链接服务）**：假设日 1 亿条生成请求，峰值写约 1 万/s、读约 10 万/s。→ 写：单机 MySQL 能扛（几千写入/s 的几倍），先单库 + 缓存；读走 Redis 缓存命中 90%+。**结论：单体 + 缓存就够了，不需要一开始就上分布式。**

> 判断要点：信封估算决定的是"需不需要分布式/分片/多活"这个量级判断，不是精确容量规划。

## 三、ADR（架构决策记录）

每个关键选型写一条 ADR，回答两个问题：**为什么这么选？放弃了什么？**

```
# ADR-<编号>：<决策标题>

## 状态
已接受 / 已提议 / 已废弃

## 背景
为什么需要做这个决策？（约束、业务上下文）

## 决策
我们选择……（一句话，具体可执行）

## 后果
- 正面：得到了什么
- 负面：放弃了什么 / 引入了什么代价
- 后续：什么时候要重新审视（触发信号）
```

示例：
```
# ADR-001：默认模块化单体，暂不拆微服务

## 背景
五人团队做月活几千的产品，无独立部署/独立扩容需求。

## 决策
采用模块化单体：单进程部署，内部按业务模块划分清晰边界。

## 后果
- 正面：部署/调试/运维成本最低，团队能快速迭代
- 负面：无法单模块扩容；代码库变大后需维护模块边界
- 后续：当出现多团队互相踩脚、或某模块需独立扩容量时重新审视
```

## 四、演进路线信号（何时升级 / 何时过度设计）

架构会"长大"，给方案时一定要给演进路线，回答两个问题：

**何时升级（触发信号）**：
- 模块化单体 → 微服务：多团队互相阻塞 / 明确独立部署需求 / 某模块需独立扩容
- 单库 → 分片：写超过单机容量 / 单表过大索引退化
- 同步 → 异步：下游变慢拖累主链路 / 需要削峰
- 加缓存：读远多于写且重复读多（命中率高）

**何时是过度设计（别做）**：
- 用户规模还小就上分片/微服务/多活
- 没有扩展需求就搞插件化/CQRS
- 为了"先进"而用新架构（说不清代价就是跟风）

## 五、经验库引导（用户说「加入经验库」时）

按 5 问沉淀实战踩坑，写入 `../experience/arch.md`（编号 U01 起递增）：

```
1. 场景：这次做了什么架构 / 遇到什么情况？
2. 坑：踩了什么坑？（具体，可复现）
3. 后果：造成了什么代价？（时间/钱/事故/返工）
4. 对策：正确做法是什么？（可执行）
5. 来源：实战 / 事故 / 文献？（便于判断可信度）
```

模板条目：
```
- **U01 标题**（[来源]）：坑 → 后果 → 对策。
```

**读取时机**：每次设计开始前（Step 1 前）Read `../experience/arch.md`，有用户经验则作为设计参考。

**git 注意事项**：经验库在 skill 目录内，`git pull` 更新 skill 前先把 `experience/` 的改动 commit 或 stash，避免被覆盖；冲突时保留双方条目、编号去重即可。
